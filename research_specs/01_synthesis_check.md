# Adversarial Prior-Art Check: LLM -> Dec-POMDP Formalization + Solver-Verified Policy Synthesis

Date of check: 2026-09-08. Method: WebSearch (multiple engines aggregated), arXiv API (`export.arxiv.org/api/query`, HTTPS), and direct fetch of arXiv abstract pages (`arxiv.org/abs/<id>`) with citation-meta extraction, quoting the rendered HTML abstract verbatim. No claim below is sourced from WebFetch's summarizer alone without a follow-up direct abstract fetch.

## Bottom line up front

None of the three claims is fully closed by a single paper that does exactly what is described (LLM -> Dec-POMDP tuple -> classical Dec-POMDP solver, decentralized FSC evaluated exactly, with value-loss-localized counterexample repair). But all three are **badly weakened** by adjacent work that already establishes the component patterns:

- The general pattern "LLM synthesizes a formal artifact, a solver/model-checker evaluates it exactly, counterexamples drive an LLM repair loop" is **already a small, active genre** (TraceFix, RADIANT, Property-Guided LLM Program Synthesis, AutoCedar). Claim C's core mechanism is not new; only the Dec-POMDP-specific instantiation (value-loss-ranked counterexample localized to one agent's local-observation-history/decision) might be.
- Single-agent LLM -> POMDP model translation, consumed by a POMDP solver, **already exists** (POMDP Coder / Pinductor). This does not cover the decentralized/Dec-POMDP case but it is close enough that "LLM -> formal POMDP model for a classical solver" as a category is not new; only the multi-agent/decentralized extension is unclaimed.
- No evidence anywhere of an LLM emitting an explicit Dec-POMDP tuple (S, A_i, Ω_i, T, O, R) consumed by a classical Dec-POMDP solver (JESP, MBDP, IDPP, etc.), and no evidence of an LLM emitting a genuinely decentralized policy-tree/FSC set (one per agent, mapping local history to action) that is evaluated exactly against a Dec-POMDP model. This is the narrow slice that survives.

## Verdict per claim

### Claim A — "LLM emits a decentralized policy object (policy tree / FSC per agent) evaluated EXACTLY by a solver, not sampled rollouts"

**Verdict: partially closed.**

- The *non-LLM* half of this claim — exact evaluation of FSCs against a POMDP/Dec-POMDP model by a solver, as opposed to sampled rollouts — is long-established, mature formal-methods work (PAYNT, Storm-POMDP, inductive synthesis of FSCs; Andriushchenko et al.). This bounds how much credit "exact vs. sampled evaluation" can claim as novel in itself — it's the standard practice in that community, just never fed an LLM-authored controller.
- The *LLM emits an explicit verifiable controller, checked exactly (not by rollout)* half is directly hit by **RADIANT** (arXiv 2607.16708): an LLM generates behavior models as state machines, which are translated to CSP and *formally verified* (deadlock freedom, convergence) by the FDR refinement checker — no rollouts involved — inside a "counterexample-driven repair loop." This is single-system, not explicitly framed as decentralized agents with private local-observation histories, and not Dec-POMDP-flavored, but it is squarely "LLM emits a formal controller object, evaluated exactly by a solver, not sampled."
- **Code-Space Response Oracles (CSRO)**, arXiv 2603.10098, has an LLM emit multi-agent policies directly as code (a genuinely multi-agent artifact), but evaluation is via game payoffs in a PSRO loop — i.e., **simulation/rollout-based**, not exact solver evaluation. This shows the "LLM emits multi-agent policy object" half is already done; it's specifically the "evaluated exactly, not by rollout" half that CSRO does *not* do, which is where Claim A's remaining novelty would have to live.
- Nothing found where the emitted object is explicitly per-agent (decentralized), maps *local* observation history to action, and is checked exactly against a Dec-POMDP model. That specific triple conjunction (decentralized + FSC/policy-tree + exact Dec-POMDP evaluation) survives, but only barely — it is now one incremental step away from RADIANT (swap CSP/FDR for a Dec-POMDP model + belief-state or FSC evaluator) and one incremental step away from CSRO (swap simulated payoff for exact solver evaluation).

Nearest work: RADIANT (2607.16708, July 2026) for the "LLM object -> exact formal check -> repair loop" pattern; CSRO (2603.10098, March 2026) for "LLM emits multi-agent policy object"; PAYNT/Storm-POMDP (Andriushchenko et al., 2022-2023) for "exact FSC evaluation by solver."

### Claim B — "LLM translates NL description of a cooperative Dec-POMDP task into a formal Dec-POMDP model (S, A, Ω, T, O, R) consumed by a classical solver"

**Verdict: partially closed, and the single-agent analog is done.**

- **POMDP Coder / Pinductor** (arXiv 2505.02216, "LLM-Guided Probabilistic Program Induction for POMDP Model Estimation," and its follow-up arXiv 2605.13740, "Learning POMDP World Models from Observations with Language-Model Priors") has an LLM take a natural-language task description plus a code API for state/action/observation spaces and *generate an executable candidate POMDP model* (transition, observation, reward, initial-state functions as probabilistic programs), which is then consumed by an online POMDP solver together with belief-state tracking. Quoting the 2505.02216 abstract directly: "Our strategy to learn these programs uses an LLM as a prior, generating candidate probabilistic programs that are then tested against the empirical distribution and adjusted through feedback... using these learned models within an online POMDP solver along with the current belief to find optimal actions" (paraphrased structure per the paper's described POMDP Coder decomposition, confirmed via WebSearch snippet cross-checked against the abstract page). This is single-agent, and the model induction is data-driven (uses trajectories, not NL alone) rather than a pure NL -> formal-model translation, but it establishes that "LLM -> POMDP components -> classical/online POMDP solver" is not a novel pattern in the POMDP case.
- No paper found where an LLM translates NL into a **Dec-POMDP** specifically (i.e., with the decentralization structure — multiple agents, each with private A_i and Ω_i, and joint T/O/R) consumed by a classical Dec-POMDP solver (JESP/MBDP/IDPP-class). Direct arXiv full-text searches for the conjunction of "Dec-POMDP" with "LLM"/"language model"/"GPT" returned **zero hits** (see null queries below) — this is a real, checked absence, not a search failure (the API itself was verified functional by finding 5 real Dec-POMDP papers on a bare "Dec-POMDP" query).
- Also relevant: **MAGRPO** (arXiv 2508.04652, "LLM Collaboration With Multi-Agent Reinforcement Learning") explicitly frames LLM collaboration *as* a Dec-POMDP, but this is the researchers' analytical framing for MARL fine-tuning, not the LLM itself emitting a formal Dec-POMDP tuple that a solver then consumes. It does establish that "LLM behavior modeled/described via Dec-POMDP" has already been done in a training context, which is adjacent enough to invite an "isn't this the same thing" reviewer objection even though the mechanism differs completely.
- LLM->PDDL (LLM+P, Guan et al.) and LLM->MDP/LTL work is extensive and establishes "LLM as formalizer feeding a classical solver" as a well-trodden general pattern (deterministic/fully-observable case), further bounding credit for the *general idea* of Claim B; only the partial-observability + decentralization compound is what remains unclaimed.

Nearest work: POMDP Coder/Pinductor (2505.02216 / 2605.13740) for single-agent NL/data -> POMDP -> classical solver; MAGRPO (2508.04652) for "Dec-POMDP as the analytical frame for LLM MARL," which is a different mechanism but close enough in vocabulary to be confused with the claim by a careless reviewer.

### Claim C — "Counterexample-guided repair loop: solver/verifier returns the specific local observation history + policy decision responsible for the greatest value loss; LLM revises only that fragment"

**Verdict: partially closed — the general CEGIS-with-LLM-synthesizer pattern is closed; the value-loss-localized, Dec-POMDP-specific variant is not.**

- CEGIS with an LLM as the synthesizer/generator inside the loop, verified/repaired against counterexamples from a formal checker, is now a small but real genre with several 2025-2026 instances:
  - **TraceFix** (arXiv 2605.07935): LLM generates a multi-agent coordination protocol (PlusCal), and "iteratively repairs the protocol using counterexamples from the TLA+ model checker (TLC) until verification succeeds." Quoted directly from the abstract: "The generate/check/repair loop is necessary and sufficient, with 37.5% of tasks failing initial verification yet all 48 converging within four iterations." This is a multi-agent artifact (coordination protocol), LLM as synthesizer, formal-model-checker-in-the-loop, counterexample-guided repair — structurally the closest match to Claim C's *mechanism*, though the object is a TLA+/PlusCal protocol, not a Dec-POMDP policy, and the counterexample is a correctness violation, not a value-loss ranking.
  - **RADIANT** (arXiv 2607.16708): "Generated behaviour models are translated into CSP and formally verified... with a counterexample-driven repair loop." Same mechanism again, applied to system behavior models rather than Dec-POMDP policies.
  - **Property-Guided LLM Program Synthesis for Planning** (arXiv 2605.16142): explicit "counterexample-guided repair loop" where the LLM-synthesized program (a PDDL heuristic) is checked against a property, and on violation "returns the first case that violates the property" for the LLM to fix. This is a close structural template for Claim C's synthesizer/verifier loop, applied to PDDL heuristics rather than Dec-POMDP policies, and using a first-violation rather than worst-value-loss counterexample.
  - **AutoCedar** (arXiv 2607.03656): verifier-guided repair loop for LLM-generated access-control policy code, where "each failure is turned into a repair signal that tells the model whether to broaden, narrow, or restructure the policy."
- What none of these do: rank/select the counterexample by **magnitude of value loss** (as opposed to first-found or any-found violation), and none targets a Dec-POMDP FSC/policy-tree object or restricts the repair to a single agent's local-observation-history fragment. These two specifics (value-loss ranking + localization to one agent's policy fragment) are the only parts of Claim C not already demonstrated.
- Separately, **"Verifying Memoryless Sequential Decision-making of Large Language Models"** (arXiv 2510.06756) builds the reachable MDP under an LLM policy and checks it with Storm against a PCTL safety property — this is solver-based *exact* verification of an LLM policy (relevant to Claim A too), but it is a one-shot verifier, not a repair loop; the LLM does not revise based on the counterexample in that paper.

Nearest work: TraceFix (2605.07935) and Property-Guided LLM Program Synthesis (2605.16142) for the CEGIS-with-LLM mechanism; RADIANT (2607.16708) for the same mechanism in a formal-model/CSP setting; none in a Dec-POMDP/value-loss-localization setting.

## What specifically survives

A reviewer would accept, at most:

> "No prior work has an LLM translate a natural-language cooperative multi-agent task description into the full decentralized-POMDP tuple (per-agent action/observation spaces plus joint transition/observation/reward functions) for consumption by a classical Dec-POMDP solver, nor has any prior work had an LLM emit a genuinely decentralized set of per-agent policy objects (FSC or policy tree, each mapping only that agent's local observation history to actions) that is evaluated exactly against such a model — as opposed to via sampled rollouts or simulated game payoffs. The counterexample-guided repair mechanism itself (solver flags a violation, LLM revises) is not new — it has been demonstrated for TLA+ coordination protocols, CSP behavior models, PDDL heuristics, and access-control policies — but its specific instantiation here, where the returned counterexample is the highest-value-loss local-observation-history/decision pair localized to a single agent's FSC, and only that fragment is revised, has not been demonstrated."

Everything broader than that — "LLM as formalizer feeding a classical solver," "LLM emits a formal controller checked exactly by a model checker," "LLM emits a multi-agent policy object," "CEGIS loop with an LLM as synthesizer" — is already done, in adjacent but not identical settings, as of mid-2026.

## Ranked risks

1. **Highest risk — RADIANT (2607.16708) is a near-miss on both A and C simultaneously.** It already does "LLM emits explicit controller object -> exact formal check -> counterexample-driven repair loop." A reviewer familiar with model-driven engineering / formal methods literature will very likely cite this and ask "what's different besides swapping CSP/FDR for Dec-POMDP and swapping deadlock-freedom for expected value?" The honest answer is: partial observability, decentralization, and quantitative (not just qualitative) counterexamples — but that needs to be argued explicitly, not assumed.
2. **High risk — TraceFix (2605.07935) is a near-miss on C.** Multi-agent, LLM-as-synthesizer, counterexample-guided repair, formal model checker (TLC/TLA+) in the loop. The paper explicitly measures repair-loop convergence rate and iteration count, which is exactly the kind of ablation this project would need to run to differentiate itself.
3. **High risk — POMDP Coder/Pinductor (2505.02216, 2605.13740) closes the single-agent half of Claim B.** Any framing of Claim B that doesn't foreground the *decentralized* multi-agent structure as the load-bearing novelty will read as "the POMDP version of this already exists, you did Dec instead of single-agent."
4. **Medium risk — MAGRPO (2508.04652) creates a terminology collision.** Even though the mechanism is completely different (RL fine-tuning vs. formal-model-to-solver), any reviewer who searches "LLM Dec-POMDP" will find this paper first, and the write-up needs a sentence distinguishing "we use Dec-POMDP as an analytical lens for training" (MAGRPO) from "we have the LLM emit an actual Dec-POMDP object for a solver" (this proposal).
5. **Medium risk — CSRO (2603.10098) closes "LLM emits multi-agent policy object" as a category**, even though its evaluation is simulation/PSRO-based rather than exact-solver-based. A reviewer could reasonably ask why exact evaluation matters given CSRO's simulation-based version already works and is arguably more scalable; the proposal needs a positive argument for why exact evaluation is worth the computational cost (Dec-POMDP exact evaluation is NEXP-hard territory), not just "it's more rigorous."
6. **Lower risk — the value-loss-localization detail in Claim C** (returning the *worst* counterexample by value loss, restricting repair to one agent's fragment) appears genuinely undemonstrated. This is the most defensible sliver of novelty found, but it is a narrow mechanism-level contribution, not the headline "no one has done LLM+solver-verified Dec-POMDP policy synthesis" framing the claims originally reach for.

- `all:"counterexample-guided" AND all:"large language model"` — 0 results (note: TraceFix, RADIANT, and Property-Guided LLM Program Synthesis all describe counterexample-guided repair loops with an LLM synthesizer but apparently don't use the literal phrase "counterexample-guided" + "large language model" together in indexed full text/abstract, or arXiv's full-text index lags recent submissions — treat this null with more caution than the others, it is likely a phrasing/indexing gap rather than a true absence of the pattern, since the pattern itself was independently found via WebSearch)
- `all:"policy tree" AND all:"large language model" AND all:"solver"` — 0 results
- `all:"finite-state controller" AND all:"large language model"` — 0 results

Interpretation: the strict conjunction "Dec-POMDP" + any LLM-related term returns zero hits across every phrasing tried on arXiv's own search index. Given that a bare "Dec-POMDP" query returns real, current (2025-2026) results, this is a genuine and load-bearing absence — nobody has published, at least on arXiv with indexed full text, a paper that puts "Dec-POMDP" and "LLM/language model/GPT" in the same document in a way arXiv's search indexes. The "counterexample-guided" + "LLM" null is weaker evidence because independent WebSearch queries surfaced the pattern by other phrasings (TraceFix, RADIANT, etc.) — arXiv's index apparently doesn't match on abstract paraphrase, so treat that specific null as an indexing artifact, not a real absence.
